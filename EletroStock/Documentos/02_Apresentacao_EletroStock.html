01. Contexto Operacional e Investigação do Problema Real

Bruno Furlan

Gargalos no Almoxarifado Elétrico

  • Controles Manuais: Anotações em papel, pranchetas soltas e planilhas duplicadas.
  • Ambiguidade de Nomenclatura: Grafias livres como "2.5", "2,5 mm" e "2.50" duplicam materiais e confundem estoquistas.
  • Ausência de Travas: Retiradas anotadas sem conferência de saldo real geram furos de estoque e saldos negativos no papel.
  • Risco Crítico à NBR 5410: Entregar condutor de 1,5 mm² no lugar de 2,5 mm² superaquece o circuito por efeito Joule e causa incêndio.
✓ Evidências de Campo (2 Técnicas Formais)

Técnica 1 — Entrevistas (4 Almoxarifes / 6 Eletricistas):

• 83,3% dos eletricistas já receberam bitola trocada por identificação confusa.

• 100% dos almoxarifes admitem anotar às pressas no pico da manhã para digitar depois.

Técnica 2 — Análise Documental (50 Requisições / 15 Inventários):

• 19,2% de discrepância média entre prateleira física e papel.

• 11 registros com saldo final negativo no papel (-8 un.).

• 17 grafias divergentes cadastradas para a mesma seção de 2,5 mm².

06. Evidências de POO: Abstração e Herança

Lucas Piva

Aplicação Prática no Domínio

  • ABSTRAÇÃO Superclasse ItemBase: Define atributos comuns a qualquer entidade do galpão (ID e Nome protegidos) e impõe contrato com método abstrato.
  • HERANÇA Subclasses Especializadas: Categoria, SecaoNominal e Produto estendem ItemBase via extends ItemBase.
  • Reuso de Código: O construtor filho invoca parent::__construct($id, $nome), reaproveitando a inicialização da superclasse.
📐 Diagrama 03 (Classes UML) & 💻 Código-Fonte Ver D03 (PDF) ↗
«abstract» ItemBase
# int id
# string nome
+ __construct(id, nome)
+ exibirDetalhes()* : string  (Contrato Abstrato)
↑ Herança: Categoria extends ItemBase ↑
ItemBase.php • Classe Abstrata:
abstract class ItemBase { protected $id; protected $nome; public function __construct($id, $nome) { $this->id = $id; $this->nome = $nome; } // Contrato obrigatório para subclasses: abstract public function exibirDetalhes(); }
Categoria.php • Herança com parent::__construct():
class Categoria extends ItemBase { private $descricao; public function __construct($id, $nome, $descricao) { parent::__construct($id, $nome); // Reuso da superclasse $this->descricao = $descricao; } }

07. Evidências de POO: Polimorfismo e Encapsulamento

Lucas Piva

Mecanismos de Segurança e Reuso

  • POLIMORFISMO Sobrescrita de exibirDetalhes(): Cada classe filha implementa sua própria apresentação conforme modelado no Diagrama de Classes.
  • ENCAPSULAMENTO Invariante de Negócio: Atributos protegidos/privados e manipulação controlada pelo setter setQuantidade().
  • MÉTODO ESTÁTICO Utilitário SecaoNominal::formatarValor(): Normaliza 4.0 para 4 sem necessidade de instanciar a classe.

08. Persistência de Dados e Transações PDO (Banco II)

Lucas Piva

Modelo Relacional e Transacionalidade

  • CATEGORIAS (1:N) → PRODUTOS: Associação obrigatória de agrupamento.
  • SECOES_NOMINAIS (0..1:N) → PRODUTOS: Chave opcional (nullable), atendendo à realidade de disjuntores e sensores sem bitola.
  • PRODUTOS (1:N) → MOVIMENTACOES: Trilha de auditoria por item movimentado.
  • Transações ACID no MySQL: Garantia de consistência contra concorrência via bloqueio FOR UPDATE.
📐 Diagrama 05 (DER Relacional) & 💻 PDO Transacional Ver D05 (PDF) ↗
Estrutura do Modelo Relacional MySQL (DER)
CATEGORIAS [PK: id] ——< (1:N) >—— PRODUTOS [FK: id_categoria]
SECOES_NOMINAIS [PK: id] —< (0..1:N) >— PRODUTOS [FK: id_secao_nominal (NULL)]
PRODUTOS [PK: id] ———< (1:N) >——— MOVIMENTACOES [FK: id_produto]
Repositorio.php • Transação Atômica com Bloqueio FOR UPDATE:
$this->db->beginTransaction(); // Início da transação atômica ACID try { // Bloqueia linha para evitar concorrência simultânea no balcão: $stmt = $this->db->prepare( "SELECT QUANTIDADE FROM PRODUTO WHERE ID = :id FOR UPDATE" ); $stmt->execute([':id' => $id]); // (...) validação de saldo e movimentação $this->db->commit(); // Confirma operação segura return true; } catch (Exception $e) { $this->db->rollBack(); // Desfaz em caso de falha }

10. Evidência Prática II: Trava de Saldo Negativo e Estorno

Higor Kleemann

Validação Transacional de Movimentação

  • Filtro Preditivo em JS: Busca incremental enquanto o almoxarife digita, acelerando o atendimento no balcão.
  • Cenário de Limite: Cabo com saldo de 15 un. → Tentativa de retirar 18 un.
  • Estorno Operacional Seguro: Reversão de saída recompõe o saldo; estorno de entrada só é autorizado se o saldo restante for $\ge 0$.
📐 Diagrama de Sequência 1 & 💻 Código de Trava Ver D04 - Seq. 1 (PDF) ↗
DS01 • Saída com Validação e Bloqueio de Saldo
1 Formulário envia: Produto ID=1, Tipo='SAIDA', Qtd=18
2 Repositorio consulta saldo atual (15 un.) via FOR UPDATE
alt [saldoAtual (15) < quantidade (18)] → Executa rollBack()
3 Controller grava $_SESSION['mensagem_erro'] e renderiza alerta
// Regra de Ouro: bloqueio transacional de saldo insuficiente if ($tipo === 'SAIDA' && $saldoAtual < $qtd) { $this->db->rollBack(); // Desfaz a transação na hora return "Saldo insuficiente! Saldo atual: {$saldoAtual} un."; }
Alerta Visual Renderizado na View:
"Erro: Saldo insuficiente! Saldo atual: 15 un."
Resultado Testado: 0 ocorrências de saldo negativo no banco de dados.
